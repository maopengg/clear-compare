# 文件锁作用域与并发恢复验证

本批处理两个分别复现的问题，没有放宽文件校验或跨进程互斥。

## 操作锁在作用域结束时显式释放

此前备份集、双向同步基线和项目会话库都返回一个已加锁的普通 File，并依靠关闭文件释放锁。Unix 的 fork/dup 可以让多个句柄引用同一把锁，仅关闭操作自己的句柄可能让继承者延长锁寿命；这符合 [Apple flock 文档](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html) 中对共享锁引用的说明。

三个入口现统一返回不可克隆的私有 FileLock，只有成功获取锁后才创建；离开作用域或 Rust unwind 时先调用 [File::unlock](https://doc.rust-lang.org/std/fs/struct.File.html#method.unlock)，再关闭句柄。调用方传入新打开的文件，不暴露可复制句柄；原本的路径、权限、摘要与版本检查不变。真正被另一项操作持有的锁仍立即返回忙错误，不等待、不重试，也不删除锁文件。

正常作用域退出的显式解锁不是进程崩溃清理保证。进程被强杀时仍依赖系统回收句柄；本功能也不能阻止不遵守锁协议的外部写入。

四个直接测试验证独立句柄互斥、旧关闭方式在复制句柄下的反例、新守卫释放及后继所有者保护、unwind 释放，以及真实子进程停在 exec 前时的继承窗口。受控子进程通过有超时的 socket 同步，避免测试失败后永久挂起。

## 崩溃测试就绪通知必须完整发布

并发排查中为原有崩溃测试增加绝对路径断言，复现到子进程发布的日志路径为空。旧通知直接 fs::write 到 ready，父进程只等待 ready 存在，可能在文件刚创建、正文尚未写完时终止子进程；之后拿空路径预览恢复，表现为文件不存在。

测试现在先写入并刷盘临时文件，再原子发布 ready；父进程仍在看到通知后立即终止真实子进程，并明确检查收到的路径。该修正只改变测试握手，没有改变生产恢复的验证逻辑，也没有把缺失恢复材料当成成功。

## 本机结果与边界

- 修正后的默认并发核心单元测试连续六次通过，每次 33 项；这些重复仅用于核对已经复现的竞争问题。
- 恢复、断点继续、双向同步与会话库 38 项集成测试通过。
- native 与 Windows GNU 目标的核心库 strict Clippy 通过。跨目标编译不代替对应系统的运行测试，本批对应 CI 仍须确认。
- 三方冲突编辑界面、交互式历史重写等产品需求仍待继续实现。完整目标见 workbench-acceptance.md。
